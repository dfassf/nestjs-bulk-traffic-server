# Kafka 실험실 계획

작성일: 2026-08-22

## 왜 만드는가

카프카가 어떤 상황에서 어떻게 동작하는지 **눈으로 보기 위해서**다.
문서로 읽은 것과 직접 죽여보고 되감아본 것은 다르다.

지금 상태로는 아무것도 볼 수 없다. `WORKER_ENGINE=kafka` 로 띄워도
프로듀서만 연결되고 작업은 여전히 Node 워커풀이 처리한다
(`/queue-stats` 의 `engineBackendWired: false` 가 이 상태를 알린다).

## 실험 소재: 주문 처리 흐름

이커머스 도메인을 **가져오는 게 아니라 상정한다.** 실제 결제 연동이나
재고 정합성이 목적이 아니라, 카프카 특성을 드러낼 재료가 필요할 뿐이다.

```
주문 생성  →  재고 차감  →  결제 승인  →  배송 시작
```

네 단계인 이유: 단계가 하나면 순서·리밸런싱 실험이 밋밋하다.
"배송이 결제보다 먼저 처리되는 사고" 같은 게 나오려면 최소 이 정도가 필요하다.

### 토픽

| 토픽 | 키 | 발행 시점 |
|---|---|---|
| `orders.created` | orderId | 주문 접수 |
| `inventory.reserved` | productId | 재고 차감 완료 |
| `payments.approved` | orderId | 결제 승인 |
| `shipments.started` | orderId | 배송 시작 |

키를 `orderId` 로 두면 한 주문의 이벤트가 같은 파티션으로 가서 순서가 보장된다.
`inventory.reserved` 만 `productId` 인 이유는 재고는 상품 단위로 경합하기 때문이다.

### 저장

기존 `BenchDriver` 는 벤치마크 전용(`benchWrite`·`benchRead`)이라 맞지 않는다.
주문용 저장소를 따로 둔다. SQLite 재사용, 테이블 2개.

```sql
orders          (order_id PK, user_id, amount, status, created_at, updated_at)
order_events    (id PK, order_id, event_type, partition, offset, consumed_at)
```

`order_events` 가 실험 관측의 핵심이다. 파티션·오프셋·소비 시각을 남겨야
"몇 번 중복 처리됐나", "어떤 순서로 왔나" 를 쿼리로 확인할 수 있다.

## 실험 목록

### 1. 파티션이 병렬성의 상한이다
파티션 6개에 컨슈머를 1→2→3→6→8 로 늘린다.
8개일 때 2개가 노는 것을 컨슈머별 처리 건수로 확인한다.

**보는 것**: 워커를 늘려도 처리량이 안 느는 지점

### 2. 리밸런싱은 전체를 멈춘다
컨슈머 3개 중 하나를 죽인다. 다시 살린다. 하나 더 붙인다.

**보는 것**: 재배정되는 동안 처리량 그래프에 생기는 계곡.
`session.timeout.ms` 를 바꿔가며 계곡 깊이 비교.

### 3. Consumer Lag 이 쌓이는 것
프로듀서 초당 1000건, 컨슈머 초당 100건으로 두고 방치.

**보는 것**: Lag 증가 곡선. 컨슈머를 늘렸을 때 따라잡는 속도.

### 4. 오프셋 되감기로 재처리
1000건 처리 후 오프셋을 처음으로 되감아 전부 다시 소비.

**보는 것**: 인메모리 큐로는 불가능한 것. 카프카를 쓰는 가장 큰 이유.

### 5. 한 이벤트를 여러 그룹이 각자 소비
`orders.created` 를 `inventory`·`settlement`·`notification` 세 그룹이 구독.

**보는 것**: 셋 다 전량 수신. 한 그룹이 죽어도 나머지는 정상.

### 6. 키가 순서를 지배한다
같은 주문의 4단계 이벤트를 키 있이 / 키 없이 발행.

**보는 것**: 키 없으면 결제 전에 배송이 처리되는 순서 역전.

### 7. 중복 처리 (at-least-once 의 대가)
컨슈머가 처리하고 오프셋 커밋 직전에 죽인다.

**보는 것**: 재시작 후 같은 주문이 두 번 처리됨.
`order_events` 에서 `GROUP BY order_id HAVING COUNT(*) > 1` 로 카운트.

### 8. Idempotent Producer
브로커를 일시 차단해 프로듀서 재시도를 유발한다.
`idempotent: false` 와 `true` 를 각각 실험.

**보는 것**: 설정 하나로 브로커의 중복이 사라지는 것.

### 9. Retention 과 Compaction
`retention.ms` 를 짧게 주고 시간이 지난 뒤 되감기 시도.
`cleanup.policy=compact` 토픽에 같은 키로 여러 번 발행.

**보는 것**: 메시지가 사라지는 것. 키별 최신 값만 남는 것.

### 10. 브로커 다운
`docker stop bulk-kafka` → 프로듀서·컨슈머 반응 → 다시 살림.

**보는 것**: 앱은 안 죽고 메시지는 남아 있는 것.

### 11. 인메모리 큐 vs 카프카
같은 주문 부하를 양쪽에 건다.

| 상황 | 인메모리 큐 | 카프카 |
|---|---|---|
| 처리 중 서버 강제 종료 | 미처리분 유실 | 남아서 재개 |
| 처리량 | ? | ? |
| 재처리 | 불가 | 오프셋 되감기 |
| 여러 소비자 | 하나가 가져가면 끝 | 각자 전량 |

이 표를 실측으로 채우는 게 이 프로젝트의 결론이 된다.

### 12. Node 컨슈머 vs Go 컨슈머
같은 토픽을 다른 그룹으로 소비시켜 처리량·지연·메모리 비교.

## 만드는 순서

| 단계 | 내용 | 이게 없으면 |
|---|---|---|
| 1 | 주문 도메인 + 카프카 배선 | 볼 게 없다 |
| 2 | Node 컨슈머 | 받을 쪽이 없다 |
| 3 | 실험 조작판 (대시보드 탭) | 매번 터미널을 쳐야 한다 |
| 4 | Go 컨슈머 | 성능 비교를 못 한다 |
| 5 | 실험 수행 + 기록 | 결론이 안 남는다 |

각 단계 끝에서 동작을 확인하고 다음으로 넘어간다.

## 실측 기록

### 파티션 분배 (2026-08-23)

파티션 6개 토픽에 컨슈머 3개를 붙였다.

```
컨슈머 0: 파티션 0, 1  →  10건
컨슈머 1: 파티션 2, 3  →  11건
컨슈머 2: 파티션 4, 5  →   9건
```

컨슈머를 8개로 늘리면 6개만 일하고 2개는 논다.

```
22223-0 처리=52
22223-1 처리=38
22223-2~7 처리=0 (할당된 파티션 없음)
```

파티션 수가 병렬성의 상한이라 서버를 늘려도 처리량이 안 느는 지점이 생긴다.

### 커밋 못 하고 죽으면 중복 (2026-08-24)

`crashAfter=20` 으로 컨슈머를 띄워 20건 처리 직후 커밋 없이 죽였다.
같은 그룹으로 재시작했더니 **파티션 0 의 오프셋 3번이 두 번 처리**됐다.

```
같은 오프셋 재처리: 1건 → p0/3
```

한 건인 이유는 이 구현이 매 건마다 커밋하기 때문이다. 커밋을 놓치는 건
마지막 한 건뿐이다. 실무처럼 배치로 커밋하면 중복 폭이 훨씬 커진다.

**실험하다 알게 된 것**

- `fromBeginning` 은 **커밋 기록이 없을 때만** 적용된다. 이미 커밋한 그룹으로
  재시작하면 이 값과 무관하게 커밋 지점부터 읽는다.
- 재시작한 컨슈머가 죽은 컨슈머와 **다른 파티션을 배정받을 수 있다.**
  그러면 중복이 안 보인다. 중복을 보려면 같은 파티션을 다시 받아야 한다.
  처음 실험에서 이것 때문에 중복 0으로 나왔다.

## 실험 조작판에 필요한 것

- 주문 발행 (건수·속도 조절)
- 컨슈머 개수 조절
- 컨슈머 처리 속도 조절 (일부러 느리게)
- 컨슈머 강제 종료 / 재시작
- 오프셋 되감기 (처음으로 / 특정 시각으로)
- Lag 실시간 그래프
- 파티션별 분배 현황
- 중복 처리 카운트

## 정해진 것

### 컨슈머 실행 방식: 별도 프로세스 + 프로세스당 N개 인스턴스

```
CONSUMER_COUNT=3 node dist/consumer.js
```

한 프로세스 안에서 kafkajs 컨슈머 객체를 여러 개 만들면 카프카는 각각을
독립 컨슈머로 본다. 파티션 분배와 리밸런싱은 이것만으로 관찰된다.

그런데 **강제 종료 실험은 별도 프로세스라야 한다.**
`consumer.disconnect()` 는 정상 종료라서 카프카에 나간다고 알리고
오프셋도 커밋하고 빠진다. 중복이 안 생긴다.
실무에서 중복이 생기는 건 프로세스가 갑자기 죽어 오프셋 커밋을 놓친 경우다.
`kill -9` 로 진짜 죽여야 재현된다.

| 실험 | 인스턴스로 가능 | 프로세스 필요 |
|---|---|---|
| 파티션 분배 | O | |
| 리밸런싱 | O | |
| 강제 종료 후 중복 | X | O |
| 커밋 직전 사망 | X | O |

같은 코드로 둘 다 되므로 프로세스를 여러 개 띄우면 인스턴스 수는 곱해진다.

### Go 컨슈머 위치: 기존 `go-engine/cmd/consumer/`

기존 워커 풀·라우터 로직을 재사용한다. 진입점만 gRPC 서버에서 카프카 컨슈머로 바꾼다.

### 주문 API

```
POST   /orders             단건 생성
POST   /orders/bulk        대량 생성 (건수·속도 지정)
GET    /orders/stats       주문·이벤트 수, 중복 건수, 프로듀서 설정
GET    /orders/events      이벤트 기록 조회 (중복·순서 확인)
GET    /orders/duplicates  중복 처리 집계
GET    /orders/:orderId    상태 조회
DELETE /orders             기록 초기화
```

### 토픽은 앱이 만든다 (브로커 자동 생성 금지)

**2026-08-23 실측으로 드러난 문제**: 브로커의 자동 생성에 맡겼더니
`orders.created` 가 **파티션 1개**로 만들어졌다(카프카 기본값).
발행은 정상으로 보이는데 60건이 전부 파티션 0으로 갔다.

파티션이 1개면 이 실험들이 성립하지 않는다.

| 실험 | 파티션 1개일 때 |
|---|---|
| 키 라우팅 | 키가 있으나 없으나 같은 파티션. 차이가 안 보임 |
| 순서 붕괴 | 재현 불가 |
| 컨슈머 분배 | 컨슈머 2개 이상이면 하나가 논다 |
| 리밸런싱 | 재배정할 파티션이 없음 |

조치:
- `docker-compose.yml` 에서 `KAFKA_AUTO_CREATE_TOPICS_ENABLE=false`
  (없는 토픽에 발행하면 `UNKNOWN_TOPIC_OR_PARTITION` 으로 시끄럽게 실패한다)
- 앱 부팅 시 `OrderTopicProvisioner` 가 파티션 6개로 명시 생성
  (`ORDER_TOPIC_PARTITIONS` 로 조절)
- 이미 있는 토픽의 파티션이 모자라면 **경고만 하고 자동으로 늘리지 않는다**.
  파티션을 늘리면 같은 키가 다른 파티션으로 가서 기존 순서 보장이 깨지므로
  사람이 판단할 일이다.

검증: 60건 발행 시 파티션 6개에 분산됨(12·12·6·7·5·18), 브로커 실측과 일치.

### 리밸런싱 계곡 (2026-08-27)

컨슈머 3개(파티션 6개, 처리지연 5ms)에 부하를 흘리면서 하나를 SIGKILL 로
급사시키고, Lag 이 0 으로 돌아올 때까지 1초 간격으로 관측했다.

**세션 만료 60초 (기본값)**

```
0~10초    Lag 0~2      멤버 3   정상
10초      급사(SIGKILL)
12~21초   Lag 59→239   멤버 3   카프카는 아직 모름. 죽은 몫이 쌓인다
21~54초   Lag 239 고정  멤버 3   세션 만료 대기. 33초간 아무 일도 안 일어난다
57초      Lag 0        멤버 2   재배정 완료, 밀린 239건을 한 번에 처리
```

**세션 만료 10초**

```
10초      급사(SIGKILL)
11~17초   Lag 27→179   멤버 3   쌓이는 구간
18초      Lag 207      멤버 2   PreparingRebalance 포착
19초      Lag 0        멤버 2   회복
```

| 세션 만료 | 계곡 폭 | 최대 Lag |
|---|---|---|
| 60초 | **47초** | 239 |
| 10초 | **9초** | 207 |

**핵심**: 계곡의 대부분은 재배정 작업이 아니라 **죽은 걸 알아차리기까지의 대기**다.
60초 설정에서 21~54초 구간은 Lag 이 239 에 얼어붙은 채 멤버 수도 3 그대로였다.
카프카는 컨슈머가 죽은 사실 자체를 모르고 있었다. 실제 재배정은 알아차린 뒤
1~3초면 끝난다.

**그래서 세션 만료를 짧게 잡으면 되는가**: 그렇지 않다. 짧게 잡으면 처리가
조금만 느려져도 살아 있는 컨슈머가 하트비트를 놓쳐 쫓겨나고, 그것 때문에 또
리밸런싱이 일어난다. 처리 시간의 변동 폭을 보고 정할 일이다.

이 값은 코드에 60초로 박혀 있어서 비교 자체가 불가능했다.
`CONSUMER_SESSION_TIMEOUT_MS` 로 빼서 조작판에서도 바꿀 수 있게 했다.

### Consumer Lag 이 쌓이고 따라잡히는 것 (2026-09-02)

컨슈머 1개(처리지연 40ms → 초당 25건이 한계)에 그보다 빠르게 발행해
Lag 을 쌓고, 발행이 끝난 뒤 컨슈머를 3개 더 붙여 따라잡는 속도를 쟀다.

```
2~8초    +104~115/초   컨슈머 1개. 발행이 처리를 앞질러 계속 밀린다
9초      발행 종료 → 컨슈머 3개 추가 (1→4)
12~14초  -124~132/초   4개가 붙어 최대 속도로 소진
15~21초  기울기 완만    남은 양이 줄어 파티션이 비기 시작
21초     Lag 0         따라잡는 데 12초
```

| 구간 | 컨슈머 | 속도 |
|---|---|---|
| 증가 | 1개 | +110건/초 밀림 |
| 감소 | 4개 | -128건/초 소진 |

**측정 설계에서 한 번 실패**: 처음에는 발행을 한 번에 1200건 넣었더니
관측을 시작하기도 전에 발행이 끝나, 0초 시점에 이미 Lag 4663 이고
그 뒤로는 감소만 보였다. 증가 곡선을 보려면 발행이 관측 구간과 겹쳐야 한다.

**컨슈머를 4배로 늘려도 4배 빨라지지 않는다**: 늘리는 순간 리밸런싱이
일어나 그동안 처리가 멈춘다(위 "리밸런싱 계곡" 참고). 늘린 직후 몇 초는
오히려 느리다.

### 오프셋 되감기로 재처리 (2026-09-02)

9130건을 전량 처리한 뒤(Lag 0) DB 기록을 비우고, 오프셋을 처음으로
되감아 같은 메시지를 다시 읽게 했다.

```
되감기 전   eventCount 9130,  Lag 0
DB 비움     eventCount 0
되감기      커밋 위치를 각 파티션의 low 로
재소비 후   eventCount 9130,  Lag 0   ← 새로 발행한 것 없이 과거를 다시 읽음
```

인메모리 큐로는 불가능한 것이다. 한 번 꺼내면 사라지므로 되돌릴 자리가 없다.

**여기서 조작판 버그를 찾았다**: 되감기가 성공했다고 나오는데 컨슈머가
한 건도 안 읽었다. 브로커를 보니 커밋 위치가 `0` 이 아니라 `-`(없음)이었다.

kafkajs 의 `admin.resetOffsets` 는 커밋 기록을 **지운다**. 지워지면 컨슈머는
커밋이 없는 것으로 보고 자기 설정(`fromBeginning`)을 따르는데, 그게 false 면
최신부터 읽어서 과거를 하나도 다시 안 읽는다. API 는 성공을 돌려주고
Lag 도 커 보이는데 실제로는 아무 일도 일어나지 않는다.

`admin.setOffsets` 로 파티션마다 갈 위치를 명시적으로 넣도록 고쳤다.
`earliest` 는 0 이 아니라 `low`(아직 남아 있는 가장 오래된 위치)를 쓴다.
retention 으로 앞부분이 지워졌으면 0 은 존재하지 않는 위치다.

### Node 컨슈머 vs Go 컨슈머 (2026-08-26)

같은 토픽을 다른 그룹으로 소비시켜 1000건을 나란히 처리했다.
컨슈머 3개씩, 파티션 6개.

| | Go | Node |
|---|---|---|
| 처리 건수 | 1000 (실패 0) | 1000 (실패 0) |
| 처리량 합계 | 411.7건/초 | 413.2건/초 |
| 건당 평균 | 약 12µs | 약 51µs |
| p95 | 약 28µs | 약 123µs |

**처리량이 거의 같은 이유**: 둘 다 카프카 전송 속도에 막혀 있다. 처리 자체는
Go 가 4~5배 빠른데 메시지가 그만큼 빨리 안 들어와서 총 처리량은 차이가 안 난다.
병목이 컨슈머가 아니라는 뜻이다. 컨슈머 성능을 가르려면 처리 지연을 넣어
(`*_DELAY_MS`) 컨슈머 쪽을 병목으로 만들어야 한다.

**Go 는 DB 에 쓰지 않는다**: 두 프로세스가 같은 SQLite 파일에 동시에 쓰면
잠금 경합이 생겨 카프카 소비 성능이 아니라 DB 잠금을 재게 된다.
중복·순서 관측은 Node 컨슈머가 맡는다.

측정하면서 고친 것:

- **처리량 분모를 컨슈머가 뜬 시각부터 재고 있었다.** 메시지를 기다리며 논
  시간이 전부 들어가서, 처리가 끝난 뒤에도 숫자가 계속 떨어졌다(3.1 → 2.5건/초).
  첫 처리부터 마지막 처리까지로 바꾸니 722~917건/초가 나왔다.
- **Node 가 `Date.now()`(1ms 해상도)로 지연을 쟀다.** 1ms 보다 짧은 처리가 전부
  0 으로 뭉개져서, p95 가 0.000ms 인데 평균은 0.043ms 인 모순이 나왔다.
  `performance.now()` 로 바꿔 Go(나노초)와 단위를 맞췄다.
- **분위수 위치를 내림으로 잡고 있었다.** p95 가 실제보다 낮게 나와 느린 꼬리가
  가려진다. 올림으로 바꿨고 두 런타임 모두 같은 규칙을 쓴다.
